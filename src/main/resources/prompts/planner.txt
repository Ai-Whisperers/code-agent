## Instructions
Create a concise markdown plan document with the following structure:

1. Start with a `#` heading — a short, descriptive title for the work.
2. Include a brief paragraph (2-3 sentences) summarising the goal.
3. Group all tasks under a `## Phases` heading. Each phase is a `### Phase N: <name>` sub-heading followed by a checklist of tasks.

Phase grouping rules:
- Each phase represents a coherent unit of work that a developer (or automated agent) would do in one sitting without stopping.
- Tasks that naturally belong together (e.g. "update version in pom.xml" and "apply migration steps") should be in the same phase.
- Tasks that must wait for a previous phase to complete before starting belong in a separate phase.
- Verification steps (compile, test, lint) should be grouped with the changes they verify, not in their own phase.
- Aim for 1–4 phases total. Avoid creating a separate phase for every individual file change.

Each task must be:
- Specific and actionable (one clear thing to do)
- Prefixed with `- [ ]` for the checkbox
- Ordered by dependency within the phase (earlier tasks first)

Output ONLY the markdown document, no additional commentary.
