## Discovery (do this FIRST)

1. Use `list_files` to understand the overall project structure.
2. Read `pom.xml` or `build.gradle` to identify the tech stack and external dependencies.
3. Read `application.properties` / `application.yml` for external service integrations.
4. Read key source files: REST controllers/resources, services, DB migration files.
5. Use `search_code` and `query_code_graph` to understand class hierarchies and call chains.
6. Use `semantic_search` to find integration points (external APIs, message queues, databases).

## Structurizr DSL to generate

Write the file `docs/architecture.dsl` using `write_file`.

The workspace must contain:

### 1. Model section
- A `softwareSystem` for this project.
- `person` elements for each distinct type of user or external actor.
- External `softwareSystem` elements for each significant external dependency
  (databases, message queues, external APIs, cloud services, identity providers, etc.).
- `container` elements inside the main software system for each deployable unit
  (e.g. web app, API service, database schema, message queue, background worker).
- Relationships between all elements with a short description and technology label.

### 2. Views section
Include these views (use short, stable keys — no spaces):
- `systemContext <systemName> "SystemContext"` — the system and its external actors/dependencies.
- `container <systemName> "Containers"` — the containers inside the system.
- One `component <containerName> "Components_<containerName>"` view for each significant
  container (e.g. the main API service). Skip trivial containers like plain databases.

### 3. Styles section
Apply sensible default styles (always use multi-line block syntax — inline `{ ... }` is not supported by the parser):
```
styles {
    element "Person" {
        shape Person
    }
    element "Database" {
        shape Cylinder
    }
    element "Queue" {
        shape Pipe
    }
    element "External" {
        background #999999
        color #ffffff
    }
}
```

## Writing guidelines

- Keep each view focused — no more than 12 elements per diagram. Split if needed.
- Use clear, concise descriptions (1 sentence per relationship).
- Use technology labels (e.g. `"HTTPS/REST"`, `"JDBC"`, `"AMQP"`, `"gRPC"`).
- Do NOT include internal implementation details (private methods, local variables).
- Do NOT reference any specific git hosting platform by name in element descriptions.
- Every element key must be a valid Structurizr identifier (alphanumeric + underscore, no spaces).
- The DSL must be syntactically valid — it will be parsed by `StructurizrDslParser` immediately
  after you write it. If validation fails, you will receive an error and must fix it.

## Process

1. Explore the codebase thoroughly.
2. Write `docs/architecture.dsl` using `write_file`.
3. Confirm the file was written successfully.
4. Provide a brief summary of what was modelled (elements, views, key relationships).
