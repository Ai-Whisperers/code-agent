## Workspace layout

The agent executing each step will have both repositories cloned into the same workspace:
- `source/` — read-only clone of the source repository
- `target/` — read-write clone of the target repository (all writes go here)

Every step prompt MUST reference paths relative to `source/` when reading and `target/` when writing. The agent must NEVER modify files under `source/`.

## Instructions

Create a concise markdown plan document with the following structure:

1. Start with a `#` heading — a short, descriptive title for the work.
2. Include a brief paragraph (2-3 sentences) summarising the goal.
3. Group all tasks under a `## Phases` heading. Each phase is a `### Phase N: <name>` sub-heading followed by a checklist of tasks.

## Phase structure by rewrite mode

### full_rewrite
Use these phases (adapt names to the actual frameworks involved):
- Phase 1: Analysis — list all source files, understand domain model, identify dependencies
- Phase 2: Scaffold — create project structure, solution/package files, configuration in `target/`
- Phase 3: Domain Layer — rewrite models, entities, value objects from `source/` into `target/`
- Phase 4: Service Layer — rewrite business logic applying SOLID principles (SRP, OCP, DIP)
- Phase 5: Infrastructure Layer — rewrite data access, repositories, external integrations
- Phase 6: API Layer — rewrite HTTP controllers, routes, request/response DTOs
- Phase 7: Tests — generate unit tests for the rewritten service and domain layers

### framework_migration
Use these phases (adapt names to the actual frameworks involved):
- Phase 1: Analysis — list all source components, understand routing and state management
- Phase 2: Dependencies & Config — update package files, configuration, build tooling in `target/`
- Phase 3: Core Components — migrate shared components, layouts, utilities
- Phase 4: Feature Components — migrate feature-specific components and pages
- Phase 5: Routing & State — migrate routing configuration and state management
- Phase 6: Tests — update or regenerate tests for migrated components

### extraction
Use these phases (adapt names to the actual bounded context):
- Phase 1: Analysis — identify all files in `source/` related to `{{SCOPE_HINT}}`; list them explicitly in the step prompt
- Phase 2: Scaffold — create project structure and configuration for the new service in `target/`
- Phase 3: Domain Layer — port domain models and value objects from the identified source files
- Phase 4: Service Layer — port business logic, applying SOLID principles
- Phase 5: Infrastructure Layer — port data access layer; define the service's own schema
- Phase 6: API Layer — port HTTP controllers; define the public API contract (OpenAPI spec if applicable)
- Phase 7: Tests — generate unit tests for the extracted service

## Step sizing rules (IMPORTANT)

Each step must touch at most 8-10 files in `target/`. If a layer has many files, split it into multiple steps (e.g. "Domain Layer — Order models", "Domain Layer — Customer models"). This is required to stay within the agent's file-change guardrail limit.

## Step prompt format

Each task in the checklist must be a self-contained instruction for the agent. Include:
- Which specific source files to read (e.g. `source/app/Services/OrderService.php`)
- Which target files to create or update (e.g. `target/src/Services/OrderService.cs`)
- The design principle or pattern to apply (e.g. "apply Dependency Inversion — inject IOrderRepository via constructor")
- The target language idioms to use (e.g. "use EF Core DbSet, not raw SQL")
- End every step with: "Commit all changes with message: `feat: <short description>`"

## Phase grouping rules

- Each phase represents a coherent unit of work (one layer or concern at a time).
- Tasks that must wait for a previous phase belong in a separate phase.
- Aim for 4-7 phases total. Do not create a separate phase for every individual file.

## Output format

Output ONLY the markdown document, no additional commentary.
