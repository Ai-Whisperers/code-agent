## Investigation Steps

1. **Retrieve job details** — use `read_db` to query the failed job and its AI call log:

   ```sql
   SELECT job_id, job_type, status, error_message, summary, created_at
   FROM job_history
   WHERE job_id = '{{FAILED_JOB_ID}}'
   LIMIT 1;
   ```

   ```sql
   SELECT iteration, model, prompt_tokens, completion_tokens, created_at,
          LEFT(response_text, 2000) AS response_preview
   FROM ai_calls
   WHERE job_id = '{{FAILED_JOB_ID}}'
   ORDER BY iteration;
   ```

2. **Read the logs** — if `logs/cloudwatch.txt` exists, read it and look for ERROR, WARN, or exception stack traces that correlate with the failure time.

3. **Trace the failure** — identify the exact exception, assertion, or unexpected behaviour. Use `search_code`, `read_file`, and `list_files` to navigate the source code and understand the affected code path.

4. **Determine root cause** — decide whether the failure is caused by:
   - A code defect (bug, missing null-check, incorrect logic, etc.) → **fix it**
   - A configuration or environment issue → **document it and stop**
   - A transient/external failure (network, third-party API) → **document it and stop**

---

## Fixing a Code Defect

If you identify a code defect:

1. Make the minimal, targeted fix. Do not refactor unrelated code.
2. Verify the build compiles and tests pass:
   ```
   ./mvnw verify -q
   ```
3. Once the fix is validated, output the following marker as the **last line** of your final message so the system can construct the branch name:

   ```
   BRANCH_SUFFIX: <short-kebab-description>
   ```

   Example: `BRANCH_SUFFIX: fix-null-pointer-in-run-fix`

   Keep the suffix short (2–5 words, kebab-case, no special characters).

{{#if JIRA_PROJECT_KEY}}
4. Reference `{{JIRA_PROJECT_KEY}}` in your commit message and PR description.
{{/if}}

## If No Code Fix Is Needed

If the failure is not caused by a code defect, write a concise summary explaining:
- What the failure was
- Why it is not a code issue
- Any recommended follow-up actions (e.g. configuration change, retry)

Do **not** create a branch or commit in this case.

## Constraints

- Only modify files that are directly related to the fix.
- Do not change test data, migration scripts, or configuration files unless the fix requires it.
- Do not introduce new dependencies without a compelling reason.
- The `read_db` tool is read-only — you cannot modify the database.
- Limit CloudWatch queries to the time window of the failure (use the `aws_cloudwatch_logs` tool for targeted follow-up queries if needed).
